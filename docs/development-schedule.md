# 4주 개발 일정

## 목표와 전제

4주 후 Android·iOS에서 로그인부터 걸음 동기화, 알 부화와 돌봄까지 이어지는 **내부 테스트용 MVP**를 완성한다. 시작 시점에는 기능·API 설계와 Firestore 데이터 계층이 준비되어 있고, Flutter 프로젝트와 업무 API는 아직 없다. 일정은 실제 시작일이 정해지지 않아 주차 기준으로 작성했다.

- 주 5일, Flutter 담당 1명과 백엔드 담당 1명이 병렬로 작업하고 기획·디자인 및 테스트를 지원받는 것을 가정한다. 인원이나 숙련도가 다르면 범위와 일정을 다시 조정한다.
- 개발용 Firebase 환경과 Android 실기기, iOS 빌드용 macOS·실기기를 1주 차에 확보한다. 건강 데이터 연동과 iOS 빌드는 실제 환경에서 확인해야 한다.
- 아래 범위는 일정 수립을 위한 제안이며, 미확정 정책과 출시 범위는 [기획 결정 사항](open-decisions.md)에서 1주 차에 확정한다.

## 우선순위

| 구분 | 범위 |
| --- | --- |
| 필수 MVP | 로그인·사용자 초기화, 홈, 걸음 권한 및 동기화, 걸음 기록, 중복 없는 보상, 알 부화·성장, 기본 돌봄, 오류·권한 안내 |
| 여유가 있으면 | 상점·보관함, 친구 코드·목록·방문, 도감, 앱 내 알림함 |
| 후속 단계 | 선물, 청혼·가족·새 알, QR, 푸시 알림, 정기 요약과 백그라운드 동기화, 스토어 출시 |

필수 기능을 먼저 연결한 뒤 여유 기능을 선택한다. 8개 화면 전체와 친구·청혼 기능까지 4주 안에 완성한다고 가정하지 않는다.

## 주차별 계획

| 주차 | 목표 | 주요 작업 | 완료 기준 |
| --- | --- | --- | --- |
| 1주 차 | 개발 기반과 핵심 정책 확정 | 로그인 방식·최초 알·걸음 목표·보상·성장·돌봄 규칙과 건강 데이터 처리 범위를 결정한다. Flutter 프로젝트, Firebase 개발 환경, 인증 및 API 연결을 구성한다. 홈·알·기록 화면의 기본 틀과 사용자·반려동물 초기화 API를 만든다. Android/iOS 걸음 읽기 권한과 개발 기기 환경을 조기에 확인한다. | 양 플랫폼에서 앱 실행 및 로그인 후 초기 알을 조회하고, 실기기 걸음 데이터 접근 가능 여부와 제약을 확인한다. 미결정 사항과 담당자를 기록한다. |
| 2주 차 | 걸음과 보상 연결 | Health Connect·HealthKit에서 일별 합계를 읽고 앱 실행·복귀 시 동기화한다. 서버에서 걸음 기록, 포인트와 성장 누적을 처리한다. 홈 목표 진행률과 일별·주간 기록 화면을 연결하고 권한·네트워크 오류를 표시한다. | 두 플랫폼 실기기에서 걸음이 홈과 기록에 반영된다. 같은 합계를 반복 전송하거나 수치가 감소한 뒤 재전송해도 이미 지급한 보상이 중복되지 않는다. |
| 3주 차 | 부화와 돌봄 완성 | 알의 누적 성장과 부화·단계 전환을 구현하고 홈 상태를 갱신한다. 확정된 기본 돌봄 행동과 상태 변화, 재접속 시 복원을 구현한다. 핵심 흐름을 통합 점검하고 결함을 수정한다. 필수 기능이 안정적이면 상점·보관함 등 여유 기능을 착수한다. | 로그인 → 걸음 동기화 → 보상·성장 → 부화 → 돌봄 흐름이 서버 데이터와 연결되고 앱 재시작 후 상태가 유지된다. |
| 4주 차 | 안정화와 내부 테스트 | Android·iOS 실기기에서 권한, 재접속, 오프라인·재시도, 날짜 변경과 중복 요청을 점검한다. 인증·데이터 접근 권한을 확인하고 주요 결함을 수정한다. 내부 테스트 빌드, 실행 안내와 남은 과제 목록을 정리한다. 여유 기능은 필수 기능 검증을 마친 경우에만 통합한다. | 양 플랫폼 내부 테스트 빌드와 테스트 결과를 공유한다. 필수 흐름을 막는 결함이 없고 미해결 문제 및 출시 전 과제가 기록된다. |

## 마일스톤과 확인 사항

1. **1주 차 종료:** 정책·환경을 확정하고 인증과 초기 데이터를 연결한다. 걸음 접근이 막히면 해당 플랫폼의 제약과 대안을 기록하고 범위를 조정한다.
2. **2주 차 종료:** 실제 걸음이 서버의 기록·보상·성장에 반영되는지 확인한다. 중복 지급 방지는 3주 차 기능보다 우선한다.
3. **3주 차 종료:** 핵심 사용자 흐름을 처음부터 끝까지 실행한다. 미완료 필수 기능이 있으면 여유 기능을 뒤로 미룬다.
4. **4주 차 종료:** 테스트 빌드와 결과, 미해결 결함을 전달한다. 스토어 심사와 정식 출시는 별도 일정으로 계획한다.

## 선행 결정과 위험

- 1주 차 초에 [D01~D05, D08~D16, D25](open-decisions.md)를 우선 결정한다. 확정 전에는 문서의 수치를 임시값으로만 사용한다.
- 실기기·계정·iOS 개발 환경을 확보하지 못하면 해당 플랫폼의 연동과 검증이 지연될 수 있다. 백그라운드 동기화는 OS 실행 시점을 보장할 수 없어 MVP에서 제외한다.
- 걸음 데이터 접근 권한과 건강 데이터 처리 정책은 플랫폼별로 확인한다. 데이터 미조회, 권한 문제와 실제 0걸음을 화면에서 구분할 수 있도록 설계한다.
- 친구·청혼·푸시를 추가하면 관계 정책, 동시 처리, 알림 설정 및 추가 테스트가 필요하므로 별도 범위와 일정을 산정한다.
